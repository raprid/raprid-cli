# fill-release-check-result

先に [共通実行ルール](../runtime.md) を読む。シェル例のパス・ツール名は同ルールに従って解決する。

リリース資料の**「確認手順」シートを実施環境で実行し、結果とエビデンスを埋める**。
入力は既にある `docs/official/<案件名>/release-procedure.xlsx`。
このスキルは**行を追加しない** — 行は `build-release-check-sheet` が起こしたものを使い、
E (結果) / F (確認者) / G (確認日) と「確認エビデンス」シートだけを触る。

土台と共通スクリプトは [release-doc-common](../release-doc-common/README.md)。
現在の行数と画像の対応は、その案件の README で確認する。

**このスキルの難所は xlsx ではなく撮影にある。** 撮ったものが本当に狙った画面か、
本当に無地か、本当に鮮明かは**撮ったあとに機械で確かめないと分からない**。
2026-01-15 に別ウィンドウ・別タブ・56px ずれ・hover の焼き付き・解像度不一致の
5 通りを実際に踏んだ。手順のほとんどはその再発防止に充てている。

## 引数

* **案件名** — `PROJ-123` など。資料は `docs/official/<案件名>/release-procedure.xlsx`
* **実施環境の URL** — `https://dev.example.com/admin` など
* **確認者名** — F 列に入れる氏名
* **実施する範囲** (任意) — 章や No. の指定。省略時は実行できる行すべて

## 実行環境を選ぶ

共通資材の README を読み、接続可能なブラウザと撮影手段を確認する。
以下の `computer` / `javascript_tool` は Claude in Chrome の例で、Codex では
実際に利用できる DOM 評価・マウス操作へ読み替える。
`shot.sh` は macOS + Chrome + 画面収録・自動操作の権限がある場合の経路。
Playwright 等で十分な解像度の PNG を撮れる場合は、その経路を使ってもよい。
ログインが必要なら人に行ってもらい、撮影機能が無ければ既存証跡の整理・資料生成まで進める。

実機操作を誰が行うかと確認者を明確にする。未確認の期待値を OK にしない。
外部連携・送信・共有環境の変更は、対象と操作が依頼に含まれる場合に限る。
対象データを使い切る操作では予備データと復元可能な範囲を先に確認する。

## 手順

### 1. 何を実行できるかを先に仕分ける

**全行の頭から順に実行しようとしない。** 実行の可否は前提で決まり、
可否の判断そのものが成果物 (結果列) になる。C 列のシナリオ ID ごとに次へ振り分ける。

| 振り分け | E 列 | エビデンス |
| --- | --- | --- |
| 画面だけで完結する | `OK` / `一部OK` / `NG` | 撮る |
| 前提を作れないと**確かめた** | `到達不可` | 確かめた画面を撮る |
| 権限・環境・データが無い | `未実施` | 無し |

`未実施` に回すのは例えば **`@manual` タグの行 / 別ロールでのログインが要る行 /
バッチの実行待ち / DB に直接触らないと作れない状態 / API コンソールが要る行**。

**取り返しのつかない操作は実行しない。** 論理削除・物理削除を伴う行は
権限があっても押さず `未実施` に回して理由を書く。
**一方向にしか進まない状態遷移は 1 行につき 1 件のデータを使い切る**
画面から元の状態へ戻せない遷移では、復元方法を先に確定する。
撮り直しが要るかもしれない行は、**先に予備のデータを用意してから**実行する。

### 2. 基準フレームを 1 枚作る

以降の撮影はすべてこの 1 枚に位置を合わせる。**目で見て正しいことを確かめた 1 枚**を
`ref.png` として置き、固定ヘッダー帯の高さ (論理 px) を DOM から測っておく。

```sh
$PY shotcheck.py ref.png                    # サイズと非空白だけ見る
```

### 3. 撮る前にページを無地にする

**エビデンスに写る「カーソル」はマウスポインタではない。**
`screencapture` は `-C` を付けない限り矢印を写さない (同一矩形を有/無で撮って差分 0)。
写るのは **`:hover` の行ハイライト**と**テキストキャレット**で、どちらも
**自分がクリックした跡**である。

`:hover` は**レンダラが最後に受け取ったマウスイベントで決まる**ので、
**OS のポインタを動かしても消えない。** 実測: ポインタを (700,500) と (1505,300) に
warp して撮った 2 枚は**バイト単位で同一**なのに、`document.querySelectorAll(':hover')`
の末尾は `TR > TD` のままで、その行の背景は `rgb(247,247,247)` だった。

消すには**本物のマウスイベント**を送る。無地の座標に `hover` を打つ:

```
computer {action: "hover", coordinate: [<本文の余白>, <本文の余白>]}
```

そのうえで `precapture.js` を `javascript_tool` で実行し、**`ok:true` を確認してから撮る**。

```
javascript_tool { text: <precapture.js の中身>, tabId: <対象タブ> }
-> {"ok":true,"hoverChain":["HTML"],"tintedRows":[],"focused":"BODY", …}
```

`ok:false` なら `hoverBad` / `tintedRows` / `focused` を見て、
**hover を打ち直す・`blur()` する・スクロール位置を戻す**。**`ok:false` のまま撮らない。**

### 4. 撮る

```sh
SHOT_PY=$PY SHOT_REF=ref.png SHOT_MATCH=localhost ./shot.sh out.png
```

`shot.sh` は AppleScript で URL からタブを選び、ウィンドウを前面に出し、
`screencapture -T 1 -x -D 1` で画面全体を撮ってから `locate.py` で切り出す。

**画面座標 (`-R`) で切らない。** ウィンドウは撮影の合間に動く
(2026-01-15 に 2 枚の間で 56 論理 px 動いた)。`locate.py` は基準フレームの
固定ヘッダー帯を画面内から相関で探して原点を決めるので、動いても追従し、
**別ウィンドウ・別タブを撮ってしまったときは一致しないので弾ける。**

1 画面に収まらないページは、スクロールしながら撮って `stitch_page.py` で繋ぐ。
`scrollTop` に数値を代入して撮ったなら `--exact 1` を使う (探索は数 px 誤マッチする)。

### 5. 撮れたものを検査する

```sh
$PY shotcheck.py out.png --ref ref.png --head 225 --nohover --table-top 300
```

* **`--ref`** — 固定ヘッダー帯が基準と一致するか (= 狙ったタブ・狙った位置か)
* **`--nohover`** — hover の焼き付きが無いか。**`--table-top` に表の始まる y を渡す**

`--nohover` は**幅と色の両方**で判定する。片方では区別できないものが 3 つあるため:
入力欄の地色は hover と同じ `rgb(247,247,247)` なので**幅**で落とし、
表のヘッダー行 (`rgb(234,233,233)`) とモーダルの覆い (`rgb(141,142,141)`) は
全幅なので**色**で落とす。**NG なら 3 に戻って撮り直す。**

### 6. 表示幅は変えずに画素密度を上げる

**「ぶれている」の原因は縮小でもドライブの上限でもなく、解像度の不一致だった。**
変更箇所シートは 1426px を 713px 幅で表示 (2 倍) しているのに、
エビデンスは 1512px を 1512px 幅で表示 (1 倍) していた。
Retina でスプレッドシートを開くと描画側が 2 倍に引き伸ばすので、
**1 倍で貼った画像だけが甘くなる。**

**2 倍で撮って 2/3 に落とし、表示は 1512px のまま置く。**

```sh
$PY normalize.py <画像...> --width 2016 --out norm/
$PY ../release-doc-common/split_tall.py norm/*.png --max 2048 --check /tmp/cuts.png
$PY ../release-doc-common/verify_cuts.py norm/                  # 接合面に文字が乗っていないか
```

**`normalize.py` -> `split_tall.py` の順を守る。** 先に分割すると切り位置が最終画素とずれる。
**幅 2016px にすると高さの上限も 2048px** になるので、**CSS で 1536px より高いページは
分割が要る** (1 倍のときは 2048 CSS px まで入っていた)。分割の要否は撮り直しで変わる。

### 7. 貼る

`manifest.tsv` を `シート名 ⇥ 順番 ⇥ ラベル ⇥ 画像パス` で書く。
**ラベルは対応する手順の No. を入れる** (`1.1 運用画面詳細 — フッター`)。
**継ぎ (分割した 2 枚目以降) はラベルを空にする。**

```sh
$PY ../release-doc-common/relayout.py <in.xlsx> shell.xlsx manifest.tsv --width 1512 --lastcol 12
$PY ../release-doc-common/place_images.py shell.xlsx <out.xlsx>
$PY ../release-doc-common/verify_floating.py <out.xlsx>
```

`verify_floating.py` は**表示幅 (EMU) の揃いと画素の長辺 2048px** を別々に見る。
**この 2 つは同じである必要はない** —— 表示 1512px・画素 2016px が狙いの形。

### 8. 結果を書く

```sh
$PY fill_results.py <xlsx> "確認手順_運用画面" man.tsv --author "氏名" --date 2026/09/04 --legend
```

マニフェストは `No. ⇥ 結果 ⇥ エビデンスのラベル行`。
**リンク先はラベル行 (`A4`) で、画像のアンカー行 (`A5`) ではない。**
`fill_results.py` はリンク先に見出しが入っているかを検証する
(空リンクはクリックするまで誰も気づかない)。

**`未実施` の行には確認者・確認日を書かない。** 誰も見ていない行に確認者名が入ると
記録が嘘になる。`到達不可` は「前提を作れないと確かめた」結果なので書く。

**`--legend` が作り直すのは確認手順シートの A2 だけ。**
確認エビデンスシートにも同じ凡例が **A3** にあり、こちらは触らない。
**結果の語彙が変わったとき (`到達不可` が消えたなど) はエビデンス側が古いまま残る**ので、
`dump_xlsx.py` で 3 シートの A3 を読んで手で揃える。
凡例は**シートごとに実際に使われた値だけ**になるので、シートを分けると内容が変わる
結果に使っていない判定値が残っていないことも確認する。

### 9. 実機で目視する

```sh
$PY ../release-doc-common/mkpreview.py <xlsx> /tmp/prev.xlsx 5 A1
open -a "Microsoft Excel" /tmp/prev.xlsx    # 14 秒待ってから前面化
```

**画像がラベル行に被っていないこと**と**結果のリンクが飛ぶこと**を見る。
資料を Google スプレッドシートで共有しているなら、**写しの再アップロードを依頼する**
(ローカルの xlsx を直しても共有側は変わらない)。
GUI が使えない場合も機械検証を終え、画像配置とリンクの実機確認は未実施と記録する。
アップロードまで依頼に含まれる場合だけ、利用可能な共有先の手段で実行する。

## 既に実施した結果を、粒度を変えた行に付け直す

**既存結果の付け直しを依頼された場合は集約する。実施・再実施を依頼された場合は実機で確認する。**
集約を再実施と報告しない。一方向の状態遷移には新しい対象データが必要になることがあるので、
依頼の範囲と利用可能なデータを先に確認する。

畳んだ 1 行の結果は、**元の行の結果から機械的に決める。**

| 元の行の内訳 | 新しい結果 |
| --- | --- |
| すべて `OK` | **`OK`** |
| `OK` が 1 つ以上あり、非 `OK` が混ざる | **`一部OK`** |
| `OK` が 1 つも無い | **`未実施`** |
| `NG` が 1 つでもある | **`NG`** (畳んで薄めてはいけない) |

* **`一部OK` にした行は「確認できた範囲」と「確認していない範囲」を README に書く。**
  資料の 1 セルには入り切らないので、読み手が判断できる場所に残す
* **`未実施` になった行は確認者・確認日を空にする** (`fill_results.py` の `NO_WITNESS`)。
  元の行に日付が入っていても、畳んだ結果が `未実施` なら消す
* **確認日は実施日を据え置く。** 組み替えた日ではない
* **落とした章に `到達不可` の行が全部入ると、その語彙が資料から消える。**
  `--legend` が実際に使った値だけで A2 を作り直すので確認手順シートは自動で消えるが、
  **エビデンスシートの A3 は残る** (上の 8 を参照)
* **エビデンスのラベル行の No. も振り直す。** 新しい No. に紐づかなくなった画像は
  `参考` にして残す (撮り直さない)。**リンク先の行番号は組み替えで動く**ので、
  `place_images.py` の後に `dump_xlsx.py` でラベル行を読んでからマニフェストを書く

**集約の対応表を README に残す。** どの行がどの行に畳まれたかが分からないと、
「実施したのに未実施になっている」ように見える。

## 判断の要点

* **2026-01-15 の Claude in Chrome 環境では撮影品質が不足した。**
  MCP の `computer` スクリーンショットは **JPEG のみ・ほぼ 1 倍・ビューポートだけ**で、
  しかも**倍率が撮影ごとに変わる非整数のリサンプル** (CSS 1512×776 -> 1528×784 = 1.0106 倍、
  1512×720 -> 1568×747 = 1.0370 倍)。**直そうとしている甘さを自分で作る。**
  CDP の `Page.captureScreenshot{captureBeyondViewport:true}` が唯一の全ページ内製経路だが、
  Chrome 136 以降は既定プロファイルで `--remote-debugging-port` を拒む (実機は 152)。
  別プロファイルを起こせば通るが**再ログイン (パスワード入力) が必要になるので採れない。**
  この経路では **`screencapture` (2 倍・可逆 PNG) を使う**。
  これは当時の環境の制約であり、十分な PNG を出せる別のブラウザ経路まで禁止しない
* **撮った画像は「狙った画面か」「無地か」「鮮明か」を別々に検査する。**
  1 つの検査で 3 つを兼ねない。ヘッダー帯の照合は無地かを見ないし、
  hover の検査は別タブを撮ったことに気づかない
* **hover はスクリーンショットの問題ではなくページの状態の問題。**
  撮り方を変えても消えない。消してから撮る
* **偽陽性を出す検査は使われなくなる。** `--nohover` の初版は入力欄の地色を拾って
  32 枚中 20 枚を NG にした。**毎回オオカミが来る検査は、撮り直しを無意味にする**
* **一方向の状態遷移を含む行は撮り直せない。** 撮り直しには新しいテストデータと
  (外部サービス 連携なら) 承認が要る。**撮り直しを求められたら、まず撮り直せない行を洗い出して伝える**
* **結果は「実行できたか」ではなく「期待値を確かめられたか」で書く。**
  一部の期待値だけ確かめられたなら `一部OK` にして、残りが何かを凡例か備考に書く

## 中断する条件

* **`precapture.js` が `ok:true` にならない** — 無地にできない理由を確かめる。
  `ok:false` のまま撮ると、あとで撮り直しになる
* **`shotcheck.py --ref` が一致しない** — 別のウィンドウ・タブを撮っている。
  **一致しないものをエビデンスにしない**
* **NG が出た** — リリース可否に直結する。**資料を埋めて終わりにせず必ず報告する**
* **取り返しのつかない操作を求められる** — 論理削除・物理削除・本番データの更新は
  権限があっても実行せず、確認する
* **一方向の状態遷移を撮り直す必要が出た** — 新しいテストデータと承認が要るので確認する
* **`未実施` が多くて資料の意味が薄い** — 何が足りないと実行できるのかを整理して確認する

## 出力フォーマット

```
# 確認結果とエビデンス 2026-01-15 (dev)

| シート | 結果 | エビデンス |
| --- | --- | --- |
| 確認手順_管理画面 | OK 1 / 一部OK 3 / 未実施 4 | 23 枚 |
| 確認手順_利用者画面 | OK 1 / 未実施 5 | 3 枚 |
| 確認手順_運用画面 | 一部OK 3 / 未実施 2 | 9 枚 |

- NG: 0 件
- 未実施の理由: @manual 10 / 別ロールのログインが要る 8 / バッチ待ち 4 / 論理削除を伴う 3 / …
- shotcheck.py: 35/35 OK (ヘッダー帯一致・hover の帯なし)
- verify_floating.py: OK (表示幅 1512px 統一・画素の長辺 2048px 以下)
- 実機目視: 済 (ラベル行との被りなし・結果のリンクが飛ぶ)
- 撮り直せない行: A-3-x など 外部サービス 連携の before/after 10 枚 (新しいデータと承認が要る)
```

**NG と未実施は件数だけで済ませず、何が足りなかったかを添える。**
資料を読む人が判断するのはそこ。

## 実施前の版に戻す

**別の環境で確認をやり直すとき**や、**実施前に手順そのものをレビューへ出すとき**は、
記入済みの資料から結果とエビデンスを落とした版を
[`blank_results.py`](../release-doc-common/README.md) で書き出す。**手で消さない。**

```sh
$PY ../release-doc-common/blank_results.py \
    docs/official/PROJ-123/release-procedure.xlsx \
    docs/official/PROJ-123/release-procedure-blank.xlsx
```

E・F・G と A2 の凡例・結果セルのリンク・エビデンスの画像が落ち、
**手順 (A〜D 列) と変更箇所シートの画像はそのまま残る**。
**出力は別名にする** (入力と同じパスはエラーになる) —— 実施した記録は消さずに両方置く。
