# build-release-diff-sheet

先に [共通実行ルール](../runtime.md) を読む。シェル例のパス・ツール名は同ルールに従って解決する。

リリース資料の**「プログラムの変更箇所」シート**を作る。
1 ファイルにつき「何を変えたか / 何のための変更か」を 1 行書き、
その下に**その差分のスクリーンショットを 1 枚**貼る。

土台と共通スクリプトは [release-doc-common](../release-doc-common/README.md)、
撮影の詳細は [shooting.md](shooting.md) にある。**先に両方読むこと。**

## 引数

* **案件名** — `PROJ-123` など。資料は `docs/official/<案件名>/release-procedure.xlsx`
* **MR の URL** — 複数可。リポジトリごとに 1 本
* **パート名とファイルの割り当て** — シートを分けるとき
  (例: 「管理画面」「利用者画面」)。省略時は 1 枚

## 手順

### 1. 土台を用意する

`docs/official/<案件名>/release-procedure.xlsx` が無ければ雛形から起こす。

```sh
$PY ../release-doc-common/init_workbook.py docs/official/<案件名>/release-procedure.xlsx "管理画面" "利用者画面"
```

**既にあるなら作り直さない。** 確認手順シートが先に埋まっていることがある。

### 2. 対象ファイルを決める

対象 MR の base/head と案件の範囲を確認してファイルを選ぶ。
このリポジトリで使われている `(<案件名>)` のコミット表記は、範囲を絞る手掛かりになる。

```sh
git log --oneline --name-only <基準ブランチ>..<ブランチ> --grep '(<案件名>)'
```

`dev...<ブランチ>` には他案件の変更が混ざる場合がある。
コミット名の grep だけでも漏れる場合があるので、MR の実差分と照合する。
単体テストのファイルも 1 ファイル 1 行 + 1 枚で載せる (まとめない)。

パートを分けるときは、2 枚目以降に出てくる共用ファイルはスクリーンショットを持たせず
「[管理画面] シートの変更と同様の変更を施している。」の 1 行で受ける。

### 3. 説明文を書く

シートの上半分。A1 に `■ 変更内容メモ` (s=2)、A3 以降に 1 ファイル 1 行。
**「何を変えたか」だけでなく「何のための変更か」を書く。**
差分を見れば分かることを書き写すのではなく、差分からは読めない意図を残す。

行数は案件ごとに変わってよい。次の手順が「最終非空行 + 2」から画像を並べるので、
**説明文を全部書き終えてから 8 に進む。**

### 4. 差分を撮る

[shooting.md](shooting.md) に従う。要点だけ:

* **Chrome 拡張では `document.hidden: true` だと撮影がタイムアウトする場合がある。**
  利用可能な機能で対象タブを前面化し、それができない場合に人へ依頼する
* **拡大は `document.body.style.zoom` ではなく diff の `font-size`** (12.6px → 21px)。
  `zoom` は仮想スクローラーの可視判定を壊す
* Chrome 拡張経路では 1 ページごとに 7 秒待つ。他の経路でも描画の完了と実スクロール位置を確認する
* 実際の `scrollTop` を読み返して記録する (最終ページは末尾で clamp される)

### 5. 連結して繋ぎ目を目視する

```sh
$PY stitch.py <spec.json> <生スクショのディレクトリ> <出力先> <prefix> <actual>
$PY seams.py  <spec.json> <出力先> <prefix> /tmp/seams.png <actual>
```

**`seams.py` の出力は 画像閲覧ツール で必ず目視する。**
**行番号が飛んでいないことを全ての繋ぎ目で確認する。ここは自動化しない** —
1 行の欠落も重複も、資料の読み手には検証できない。

### 6. 高さ 2048px を超えた画像を分割する

**連結後の高さが 2048px を超えたら、そのファイルは複数枚に分ける。**
Google ドライブ上ではここを超えたぶんだけ画質が落ちる (「[判断の要点](#判断の要点)」)。

```sh
$PY ../release-doc-common/split_tall.py <assets>/*/*.png --dry-run                # まず何枚に割れるか見る
$PY ../release-doc-common/split_tall.py <assets>/*/*.png --check /tmp/cuts.png
$PY ../release-doc-common/verify_cuts.py <assets>                                 # 疑い 0 か所 になること
```

`split_tall.py` は**文字の乗っていない走査線**を選んで切り、`<元の名前>-1.png` …
`-N.png` を出す。2048px 以下の画像は触らない。P モード (256 色) の crop はパレットを
引き継ぐので、切っても再量子化は起きない (繋ぎ直せば元と画素単位で一致する)。

**`--check` の画像を 画像閲覧ツール で目視する。** 切り位置の前後 40px を並べた 1 枚が出る。
走査線の判定は経験則なので、**自動化された OK で済ませない。**
`verify_cuts.py` は書き出した PNG を読み直して接合面を独立に検査するもので、
**実際にこれで切り損じを 2 か所見つけた** (アルゴリズムの自己申告では見つからなかった)。

`split_tall.py` は最後にマニフェスト用の行を出すので、そのまま次の手順に渡せる。

### 7. マニフェストを書く

1 行 1 枚のタブ区切り。`シート名 ⇥ 順番 ⇥ ラベル ⇥ 画像パス`

```
プログラムの変更箇所_管理画面	1	api src/admin/admin-admin.service.ts	.../admin/01-api-admin-admin.service.ts-1.png
プログラムの変更箇所_管理画面	2		.../admin/01-api-admin-admin.service.ts-2.png
プログラムの変更箇所_管理画面	3		.../admin/01-api-admin-admin.service.ts-3.png
```

**並びは説明文と同じ順にする。** ラベルはそのまま画像の上の行 (20pt 太字) になる。

**分割した 2 枚目以降はラベルを空にする。** `relayout.py` はこれを「継ぎ」と解釈して、
ラベル行も空行も挟まずに直前の画像の真下に置く。**見た目は 1 枚に繋がる**ので、
`(1/3)` のような連番は付けない (読み手に分割を見せる必要はない)。
1 行目のラベルは空にできない。

### 8. 器を作って画像を貼る

```sh
$PY ../release-doc-common/relayout.py <in.xlsx> /tmp/shell.xlsx <manifest.tsv>
$PY ../release-doc-common/place_images.py /tmp/shell.xlsx <out.xlsx>
```

`relayout.py` が**土台** (A〜L を結合したセル) とラベル行・列幅・行高を作り、
`place_images.py` がその土台に `oneCellAnchor` + 明示 `<ext>` で画像を**実寸**で貼る。
2 段に分かれているのは、土台の行数を画像の実寸から決める段と画像を埋め込む段を分けて、
`<shell.xlsx>.plan` で「どの土台にどの画像を何 px で置くか」を確認できるようにするため。

**`twoCellAnchor` は使わない。** 左上と右下のセルだけを持つ形は `<a:stretch/>` と併せて
「その矩形に引き伸ばす」意味になり、矩形の高さは**行高の合計**から決まる。
行高に下限を持つ描画系 (Google スプレッドシート等) では矩形が変わって**縦横比が崩れ、
画像がラベル行に被る**。`oneCellAnchor` なら大きさは `<ext>` の実寸で決まるので歪まない。

**土台は 18.0pt (24px) の行だけで組み、画像の高さを行単位で切り上げる。**
端数を最終行の行高で吸収すると 0.38pt のような行ができ、それを丸める描画系で土台が縮む。
切り上げてあれば土台は必ず画像以上の高さになり、余った分は下端の余白になる
(画像は伸縮しないので余白が出ても崩れない)。

**貼り直しにも使える。** 前回の A〜L の結合が残っているシートでは、`relayout.py` が
その先頭行の 1 つ上を開始行に取り、それ以降のセルを白紙に戻してから組み直す
(前回のラベル行が新しい矩形の中に取り残されるのを防ぐ)。

**既に配ってしまった資料を直すときは `fix_anchors.py`。**

```sh
$PY ../release-doc-common/fix_anchors.py <in.xlsx> <out.xlsx>     # 行番号もセルの中身も動かさずアンカーだけ組み替える
```

器から作り直すと行番号が動き、確認手順シートからのリンクが外れる。
**行数が足りない画像があれば止まる**ので、そのときは器から作り直す。

### 9. 検証する

```sh
$PY ../release-doc-common/verify_floating.py <out.xlsx>          # 判定: OK / 高さ 2048px 超: 0 枚 になること
$PY ../release-doc-common/mkpreview.py <out.xlsx> /tmp/prev.xlsx 1 A1
open -a "Microsoft Excel" /tmp/prev.xlsx   # 14 秒待ってから前面化して目視
```

`verify_floating.py` が見るのは、`oneCellAnchor` + `<ext>` になっているか・`<ext>` の
縦横比が画像の実寸と合っているか・画像が土台の中に収まっているか (= ラベル行に被らないか)・
**土台の行がすべて 18.0pt か**・重なり・間隔・横幅の統一・文字セルとの干渉・画像の高さ。
**実機目視の有無を明記する。** GUI が使えない場合も生成・機械検証を終え、実機目視は未実施として引き渡す。

目視は `screencapture -x -o /tmp/excel.png` で撮って 画像閲覧ツール で見てもよい。
**継ぎのある画像は継ぎ目の行を `mkpreview.py` の第 4 引数に渡し**、上下が段差なく
繋がっていることを確かめる (AppleScript の `scroll row` は `-10006` で通らない)。

**既に画像が貼ってある資料を組み直したときは、他のシートが無傷かを dump で確かめる。**
`relayout.py` は openpyxl の往復なので、zip を直接叩いて作ったシート
(`build-release-check-sheet` の確認手順シートなど) が書き換わりうる。

```sh
$PY ../release-doc-common/dump_xlsx.py <in.xlsx>  > /tmp/dump.before.txt   # 差し替える前に
$PY ../release-doc-common/dump_xlsx.py <out.xlsx> > /tmp/dump.after.txt
diff /tmp/dump.before.txt /tmp/dump.after.txt
```

**`&#10;` が `\n` になる差分は無害** — 数値文字参照と生の改行で、XML としては同じ値。
不安なら openpyxl で両方を開いてセルの値・書式・結合・列幅を突き合わせる
複数シートがある場合は、各シートを同じ基準で照合する。

### 10. `assets/` に出して索引を書く

貼った画像と同じものを `docs/official/<案件名>/assets/<パート>/` に置き、
`assets/README.md` に**貼付順・シート・アンカー行・寸法の表**を書く。
**xlsx は grep できない**ので、これが唯一の索引になる。

**分割したファイルは断片ごとに 1 行**書き、元は 1 ファイルであることが分かるように
まとめる (`1 / 3` のように枚数を添える)。断片ごとの高さを載せておくと、
あとから「2048px 以下か」を README だけで確かめられる。

## 判断の要点

手順に落とせない、しかし外すと作り直しになるもの。

* **Excel には 0.5 倍 (幅 713px) で貼る。** スクショは 1x で保存されるので、
  Retina で等倍配置すると 2 倍に引き伸ばされて補間がかかり文字がにじむ。
  0.5 倍なら画像の 1 画素が画面の 1 画素に 1:1 で当たる。
  **見かけが半分になるぶん、撮影時に `font-size` を上げてあることが前提。**
  等倍配置は印刷にも向かない (1426px = 377mm で A3 横でも溢れる)
* **セル内画像 (Excel の「セルに配置」) は使えない。**
  Microsoft 365 のサブスクリプション (サインイン) が無いと `#UNKNOWN!` になる。
  バージョンの問題ではなく、XlsxWriter が生成した正規のファイルでも再現する。
  **配布物には使えない**ので浮動画像 (`oneCellAnchor`) で貼る
* **画像の大きさは `<ext>` の実寸で決め、行高からは決めさせない。**
  `twoCellAnchor` + `<a:stretch/>` は「結合セルの矩形に引き伸ばす」意味なので、
  行高を丸める描画系では**縦横比が崩れてラベル行に被る**。
  画像は `oneCellAnchor` + `<ext>` に組み替える
  (`fix_anchors.py`)。**結合セルは「画像を収める矩形」ではなく「画像を置く土台」**として、
  18.0pt の整数行だけで画像より必ず高く作る。端数行 (0.38pt 等) を残すと土台が縮む
* **減色は `FASTOCTREE` + `dither=NONE`。`MEDIANCUT` は使わない。**
  PIL の `MEDIANCUT` は `dither` の指定に関わらず必ず誤差拡散をかけるため、
  べた塗りの背景にノイズが載って PNG が圧縮できず、同じ 256 色でも約 1.8 倍になる。
  仕上げに `oxipng` (可逆、`level=4` で頭打ち) でさらに約 1 割。
  **それ以上は画質を削る** — 色数 32 は背景の色みが変わり、
  「べた塗りの代表色に画素を吸わせる」前処理は平均誤差が小さいのに
  文字の最も明るい画素だけを背景に潰した。**非可逆な手は平均ではなく最大誤差で測る**
* **連結した 1 枚の高さは 2048px 以下に抑える。Google ドライブ上での画質はこれで決まる。**
  Google スプレッドシート (Office 編集モード) は画像データを**長辺 2048px に縮小してから**
  配信するので、高さ 2092px を超えると**幅が 1426px から崩れ**
  (高さ 10822px なら 269px)、表示枠の 1396 デバイス px に引き伸ばされる。
  **劣化は高さに比例する**ため、1 ファイルの差分が長いときは
  「1 ファイル 1 枚」を崩して**複数枚に分ける**。
  Excel だけを見て判断すると (中身は無傷なので) この劣化に気付けない。
  分割は `split_tall.py` が行い、**ラベルを空にした継ぎとして真下に並べるので
  読み手には 1 枚に見える**。「1 ファイル 1 枚」は資料の見た目としては保たれる
* **「アップロードすると画質が悪い」はまずどこで見て粗いのかを切り分ける。**
  ダウンロードして Excel で開けば意図どおりに見えるなら、ファイルの中身ではなく
  **共有先のレンダラか配信経路が原因**。
  **「プレビューは Retina で描かない」と決めつけない** — 一度その説で結論を出して外した。
  `devicePixelRatio` と `img` の `naturalWidth/Height` を実測して確かめる
* **「見え方」の指摘は、まず本当にそこが壊れているかを機械的に確かめる。**
  「A〜L が結合されていない」という指摘を受けたことがあるが、結合は最初から正しく、
  **画像が表示されないせいで結合が見えていなかった**だけだった

## 中断する条件

* **タブが非表示で撮影できない** — 対象タブを前面化する。機能や権限が足りないときだけ人へ依頼する
* **繋ぎ目に行番号の欠落や重複がある** — 撮り直す。繋いだまま先に進めない
* **`verify_floating.py` が NG** — `<ext>` の比がずれている / 画像が土台から出ている /
  土台に端数行がある。`fix_anchors.py` で直るか、器から作り直す
* **`verify_cuts.py` が疑いを出した / `--check` で文字が裂けている** — 切り位置を直す。
  裂けた画像を貼ったまま先に進めない
* **載せるファイルの取捨に判断が要る** — 他案件のコミットが混ざっているときは確認する

## 出力フォーマット

```
# プログラムの変更箇所 2026-01-15

対象: PROJ-123 / api !123 (11 ファイル) + frontend !456 (6 ファイル)

| シート | ファイル | 画像 |
| --- | --- | --- |
| プログラムの変更箇所_管理画面 | 7 | 16 枚 (A13:L46 ほか) |
| プログラムの変更箇所_運用画面 | 11 | 18 枚 (A17:L53 ほか) |

- 繋ぎ目: 12 か所すべてで行番号の連続を確認
- 分割: 9 ファイルを 26 枚に (接合面 17 か所 / 疑い 0 か所・--check を目視)
- verify_floating.py: OK (oneCellAnchor 16 枚 / 縦横比のずれ 0EMU / 横幅 713px 統一)
- 高さ 2048px 超: 0 枚 (Google ドライブ上でも劣化しない)
- 実機目視: 済 (Excel 100% で表示・継ぎ目に段差なし)
- xlsx: 7.1MB
```

**未実施のものは「済」と書かない。** 実機目視と繋ぎ目の確認は人 (または画像を見るエージェント)
が実際に見たときだけ済とする。
