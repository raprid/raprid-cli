# build-release-check-sheet

先に [共通実行ルール](../runtime.md) を読む。シェル例のパス・ツール名は同ルールに従って解決する。

リリース資料の**「確認手順」シート**を `docs/feature/` の Gherkin 手順書から起こす。
**画面ごとに 3〜4 の大項目を立て、大項目 + サブ項目 = 1 行**に畳む
(No. は `1.1` / `2.1`…`2.4` / `3.1` の形で、整数部が大項目、小数部がサブ項目)。
**シナリオ ID は C 列の末尾にまとめて併記する。**
結果・確認者・確認日は空欄のまま置き、[fill-release-check-result](../fill-release-check-result/SKILL.md) が実施して埋める。

土台と共通スクリプトは [release-doc-common](../release-doc-common/README.md)。
既存資料がある場合は、行数と現在の構成を案件の README で確認する。

**ここは機械変換では済まない。** 手順書は実装者がローカル環境で確かめるために書かれており、
資料は**受託元が「何を見ればよいか」を 3〜4 の観点で受け取る**ためのもの。
読み替えと畳み込みが仕事の中心にある。

## 引数

* **案件名** — `PROJ-123` など。資料は `docs/official/<案件名>/release-procedure.xlsx`
* **パートごとの feature ディレクトリ** — `確認手順_運用画面=docs/feature/operator/external-link` の形。
  複数ディレクトリを合わせるときはカンマ区切り
* **実施環境** — 「開発環境」「ステージング環境」。A1 の案内文になる

## 手順

### 1. 土台を確認する

`docs/official/<案件名>/release-procedure.xlsx` が無ければ雛形から起こす
(`init_workbook.py`、`--env` で環境名を指定)。
**既にあるなら作り直さない。** 変更箇所シートに画像が貼ってあることがある。

**シートを足す・改名するときは `edit_sheets.py`** (画像パートに触らずに
`workbook.xml` だけ書き換える)。パートを 1 枚のシートに混ぜるより、
**パートごとにシートを分けたほうが読み手が追える。**

### 2. 粒度を決める — 1 画面 3〜4 の大項目

**まず「読み手が何を見れば確認したことになるか」を 3〜4 の大項目に書き出す。**
feature ファイルを 1 つずつ行にしてはいけない。例えば 1 画面を次のようにまとめる。

```
1. フッターの確認
   1.1 "確定" ボタンがないこと
2. 連携ボタンの活性化状態確認
   2.1 連携先未設定時は非活性
   2.2 SJIS 変換不可 + パッケージ表記が空では非活性
   2.3 編集依頼済ステータスでは非活性
   2.4 全条件を満たすとき活性
3. 連携ボタンを押下して連携できること
4. (必要ならパート固有の派生)
```

* **同じ観点を状態別に確かめるシナリオは 1 行に畳む。**
  「要対応から」「作業中から」「確定から」は活性条件としては同じ 1 行 (2.4)
* **「活性になる全条件」は行の中で `(1)`〜`(4)` と列挙する。**
  条件が実装のどこで決まるか (`canLink` など) を調べて書き切る。
  条件を落とすと読み手が判断できない
* **画面が同じコンポーネントを共有していても、パートごとに書き切る** —
  「管理画面と同様」で済ませると読み手が往復する。
  シナリオ ID を持たない行になってよい (下の 4 を参照)
* **落とす大項目は作らない。** 資料に載せない章は章ごと落とす (次の 3)

**粒度の目安は資料全体で 20 行以下。** 同じ資料群の中で粒度が揃っていることを優先する。

> **「1 シナリオ = 1 行」は細かすぎる。** 読み手が観点を組み立て直さなくて済むように畳む。
> 細かいシナリオは `docs/feature/` に残るため、資料側で畳んでも情報は失われない。

### 3. 載せる章と載せない章を決める

feature をファイル名順に並べ、資料に載せないものを決める。落とすのは例えば:

* **環境構築だけの章** (colima 起動・`docker compose up`・`psql` 接続)
* **回帰確認 / 一覧表示 / エラーケース / 権限 / 他パートへの影響の章** —
  今回の変更点そのものではないもの。**畳んだ大項目のどれにも入らない**
* **同時リリースすると必ず NG になる章** — 片方のパートを先行実装した時点の前提で
  書かれているもの
* **畳んだ行が同じ挙動を見ている章** — 「確定済みからの再連携」は活性条件として 2.4 で、
  「提出物一覧からの除外」は複合の行で見ている

**落とした章とその理由を `docs/official/<案件名>/README.md` に必ず残す。**
資料だけ見ると「抜けている」としか読めないため、除外理由も成果物の一部として残す。

**No. は章番号と対応しない。** 大項目は画面の観点で立てるので、
突き合わせは**シナリオ ID 側だけ**で行う。

### 4. 行に起こす

`rows_<パート>.txt` に 1 行 1 サブ項目で書く。区切りは `|`、4 列。

```
No.|画面|確認手順|期待値
2.4|管理画面詳細|…を開き、外部サービス連携ボタンを見る。\n(1) 連携先が選択されている (2) MSステータスが…|ボタンが活性になる。(A-2-1) (A-2-2) (A-2-3) (A-2-5)
```

セル内改行は `\n` でエスケープする。ここでやること:

* **C 列の末尾にシナリオ ID を `(A-1-1)` の形で並べる。**
  これが資料と手順書を突き合わせる唯一の鍵で、検証もこれ 1 本で通す。
  **1 行が複数の ID を持つ**のが畳んだあとの普通の姿
* **手順書の環境を実施環境に読み替える。** ローカル + `psql` 前提の手順は
  画面操作と画面表示に置き換える (文言は 1:1 にならなくてよい)
* **手順文中の相互参照を資料側の No. に振り直す。**
  章単位の「1. の状態から」は「2.1 の状態から」にする
* **期待値は畳んだぶんを合成する。** 1.1 のように 5 つのシナリオを 1 行にした場合は、
  見るべきことを 1 セルに並べる (「確定ボタンが無い / 連携先未選択では非活性 /
  左のボタンは従来どおり / 幅を狭めても崩れない / 連携済ではラベルが変わる」)
* **ID を 1 つも持たない行があってよい。** 共有コンポーネントを別パートで書き切った行が
  これになる。`※` で「シナリオは<他パート>の No.x.y で担保している」と添え、
  **README にも理由を残す**
* **実施に前提が要る項目は `※` で理由を添える** (受託元アカウントが要る / バッチ待ち /
  特定ロールのユーザーが要る / 論理削除を伴う / 画面から到達できない)。
  **落とさずに残す**

### 5. 形式を検証する

```sh
awk -F'|' 'NF!=4{print NR": "$0}' rows_admin.txt       # 4 列でない行
cut -d'|' -f1 rows_admin.txt | sort | uniq -d          # No. の重複
```

### 6. 貼る

```sh
$PY split_steps.py <xlsx> "確認手順_管理画面=rows_admin.txt" \
  "確認手順_利用者画面=rows_user.txt" "確認手順_運用画面=rows_operator.txt"
```

**zip の中で該当シートの XML を 1 パートだけ差し替える。**
`.bak` を作ってから書き換えるので、失敗したら戻せる。

### 7. 検証する

```sh
$PY verify_steps.py <xlsx> \
  "確認手順_管理画面+確認手順_利用者画面=docs/feature/admin/item-edit,docs/feature/account/profile" \
  "確認手順_運用画面=docs/feature/operator/item-list" \
  --skip 00-setup.feature --skip 08-regression.feature
```

**C 列のシナリオ ID の集合が feature のタグと完全一致すること**が本体。

* **`+` でシートを束ねる。** 1 つの feature ディレクトリを複数シートで分担するとき
  （1 つの feature 群を管理画面と利用者画面の両方で分担する場合）は、
  **束ねた側で ID を合算して比較する。** 片方ずつでは集合一致が通らない
* **`--skip` は資料に載せない章のファイル名。** 落とした理由は README 側に残す。
  `--skip` に並ぶ数が増えたら、粒度の判断 (上の 2) を見直す合図
* あわせて E・F・G が空 (行 4 から)、A〜D が非空、`ht` が無い、No. が文字列、
  **他シートの画像と結合が巻き添えで消えていないこと**を**シートごとに**見る
* **結果を記入した後に回すと E・F・G の「空でない」が全部 NG になる。**
  これは設計どおりで、**そのときに見るのはシナリオ ID の行だけ** (`grep 'シナリオ ID'`)。
  組み替えのように記入済みの資料を直す場合はこの読み方にする

### 8. 実機で目視する

```sh
$PY ../release-doc-common/mkpreview.py <xlsx> /tmp/prev.xlsx 3 A1
open -a "Microsoft Excel" /tmp/prev.xlsx   # 14 秒待ってから前面化
```

**折り返しが見切れていないこと**を確かめる。行高は固定していないので、
Excel が `wrapText` に応じて自動で合わせているはず。
**畳んだ行は 1 セルが長い**ので、目視の有無を必ず報告する。
GUI が使えない場合も生成・ID 照合は終え、折り返しは未確認として対象シートを示す。

## 判断の要点

* **粒度は資料群の中で揃える。** 他の案件の資料が 3 行なら、こちらも 3〜4 の観点で渡す。
  細かさは `docs/feature/` の手順書が持ち、資料は観点だけを持つ
* **`ht` / `customHeight` を付けない。** 付けると高さが 18pt に固定され、
  折り返した C / D 列が見切れる。属性が無ければ Excel が内容に応じて合わせる
* **No. は `t="inlineStr"` の文字列にする。** 数値にすると `1.10` が `1.1` に丸められる
* **文字を直すのは zipfile で 1 パートだけ。** 確認手順シートは全セルが `t="inlineStr"` で
  `sharedStrings.xml` に依存しないのでこれが成立し、**画像に一切触らない**。
  openpyxl の往復でも `oneCellAnchor` のアンカーは落ちないが (実測)、
  17MB の画像を読み書きし直すぶん遅く、壊れたときの影響が資料全体に及ぶ
* **検証はシナリオ ID の集合一致 1 本でよい。** 行数が変わっても抜けと重複がこれで捕まる。
  **畳んでも集合は変わらない**ので、粒度を変える組み替えでもこれがそのまま効く
* **feature のタグは `@A-3-3 @manual` のように 1 行に複数並ぶ。**
  行末までを要求する正規表現で拾うと偽の不一致が出る

## 中断する条件

* **シナリオ ID の集合が feature と一致しない** — 意図して落とした章なら `--skip` に足す。
  そうでなければ起こし漏れ。**一致しないまま先に進めない**
* **大項目の立て方が決まらない** — 画面と観点の対応が付かないときは確認する。
  ここを外すと行を全部書き直すことになる
* **「活性になる全条件」が実装から読み切れない** — 条件を落として書くより確認する
* **環境の読み替えに判断が要る** — 手順書がローカル固有の操作 (SQL の直接実行など) を
  前提にしていて画面に置き換えられないとき
* **載せない章の判断が付かない** — 他パートとの同時リリースで結果が変わる章

## 出力フォーマット

```
# 確認手順 2026-01-15

| シート | 出所 | 大項目 | 行数 |
| --- | --- | --- | --- |
| 確認手順_管理画面 | docs/feature/admin/item-edit + docs/feature/account/profile | 4 | 8 |
| 確認手順_利用者画面 | 同上 (共有コンポーネント) | 3 | 6 |
| 確認手順_運用画面 | docs/feature/operator/item-list | 3 | 5 |

- 載せなかった章: 17 章 (回帰 / 一覧表示 / エラーケース / 権限 / 他パートへの影響ほか。理由は README)
- ID を持たない行: 利用者画面 4 行 (管理画面の No.2.1〜2.3 / 3.1 で担保)
- verify_steps.py: OK (ID 集合 24/24・17/17 一致、E・F・G 空、画像 69 枚と結合 49 個を維持)
- 実機目視: 済 (折り返しの見切れ無し)
```

**結果・確認者・確認日は空欄のまま渡す。**
記入とエビデンスの添付は [fill-release-check-result](../fill-release-check-result/SKILL.md) が行う。
**既に記入済みの資料から空欄の版を作り直したいときは
[`blank_results.py`](../release-doc-common/README.md) を使う** (手で消さない)。
