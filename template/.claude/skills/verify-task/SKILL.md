# verify-task

先に [共通実行ルール](../runtime.md) を読む。

`docs/feature/` 配下の手順書を読み、**人が実機を操作して、エージェントが指示と判定の選択肢を出す。**
このスキルはブラウザを触らない (エージェントが自分で操作するのは run-manual-test の担当)。

手順の実体は `docs/feature/<領域>/<機能>/<章>.feature`、タスクとの対応はタスク md の
frontmatter `test:`、結果は `job/<案件名>/assets/<タスク名>/<実行日>/`。
記法は [docs/feature/README.md](../../../docs/feature/README.md) に従う。

**エージェントが代わりに判断しないのが肝。** 画面を見ているのは人だけなので、
「たぶん OK だろう」で先に進むと確認したことにならない。
選択肢を出して選んでもらい、選ばれたものだけを結果にする。

## 引数

* **タスク名** — 対象のタスク。部分一致で探し、複数該当したら候補を挙げて確認する。
  省略時は `progress` のタスクから選ばせる (`test:` が空のものは候補に出さない)。
* **シナリオ ID / 章** — `P-1-1` や `P-1` のように指定された場合はそれだけを回す。
  省略時は全シナリオ。**再確認では章単位の指定が多いので、必ず受け付ける。**

## 手順

### 1. 対象を決める

タスクの実体から `test:` を読み、feature の一覧に展開する。
ディレクトリなら `_` で始まらない `.feature` をファイル名順に全部。

```sh
J="job/<案件名>"
sed -n '/^---$/,/^---$/p' "$J/list/<タスク名>.md"
ls docs/feature/<領域>/<機能>/
```

`test:` が空で、タスク md の本文に Gherkin が埋まっている場合は
**`docs/feature/` への抽出を提案して、そこで止まる。** 勝手に移動しない
(どの機能ディレクトリに置くかは人が決めた方がよい)。

`test:` も本文の Gherkin も無ければ、手順書が無いということなので
「手順書を作るところから始めますか」と聞いて終える。

### 2. 前提を確認する

`_background.feature` の `Background:` と、対象の章が持つ独自の `Background:` を提示し、
**不足している前提だけを質問ツールまたは会話でまとめて聞く。** ブランチ・コンテナの起動・ログインロール・
対象データの ID がここで揃う。

```sh
cat docs/feature/<領域>/<機能>/_background.feature
git -C repos/<repo>/repo rev-parse --short HEAD
```

**揃っていないものがあればそこで止める。** 前提が崩れた状態で回した結果は使えない
(「章 8 は管理画面の対応が入っていないブランチでないと成立しない」のような
前提が実際にある)。

`@destructive` の章が含まれる場合は、**何が変わるかを先に伝えて確認を取る。**
ログインユーザーの権限、他の行、論理削除が対象になる。

### 3. シナリオを 1 つずつ回す

シナリオごとに `Given` / `When` を**通し番号つきでそのまま提示する。**
言い換えない — 番号は「P-3-2 の (5) で NG」と指すためのものなので、崩すと使えなくなる。
SQL は `sh` か `sql` のフェンスで貼り、そのままコピーできる形にする。

そのうえで `Then` を判定の選択肢にする。

| `Then` の数 | 聞き方 |
| --- | --- |
| 4 つ以下 | 各 `Then` の結果を聞く。複数選択 UI が無ければ「すべて期待どおり / 一部が違う / 確認できない」と、該当番号を答えてもらう。未選択は未回答であり NG ではない |
| 5 つ以上 | まず「すべて期待どおり / 一部が違う / 確認できない」の3択。「一部が違う」なら次の質問でどれが違ったかを絞る |

* 選択肢のラベルは `Then` の要点を短く、`description` に `Then` の全文を入れる
* **どの場合も「確認できない」を選択肢に入れる。** モックの制約や環境の都合で
  到達できないシナリオが実際にあり、それは NG ではない
* **NG のときだけ**「何が起きたか」を追加で聞く。OK は選ばせるだけで先に進む

**同じ `Given` を共有し、画面を見るだけのシナリオ (章 1 の 4 件のような) は
利用可能な質問ツールの上限に収まる範囲でまとめてよい。**
状態を変えるシナリオは 1 問ずつにする (前のシナリオの結果が次の前提になるため)。

`@manual` タグのシナリオもこのスキルでは普通に回す
(自動化できないだけで、人がやるなら問題ない)。

### 4. 後片付けを回す

**ここは飛ばさない。** 過去に、テスト中の操作で管理画面が論理削除されたり
重複行が自動生成されたりして、復元に手間が掛かった実例がある。

その回で流した `UPDATE` と、画面から行った操作を「環境の復元」表にまとめ、
**1 件ずつ戻したかを確認する。**

| 対象 | 変更内容 | 復元 |
| --- | --- | --- |
| `items` id=100 | `status` draft → active | 初期値に戻したか |
| `users` id=1 | `role_id` 1 → 3 | 戻したか |

後片付けのシナリオ (`04-teardown.feature` のような) が手順書にあればそれを使う。
無ければ、実行前に記録した対象行の値と、その回の操作履歴から復元手順を作る。
変更前の値が不明なら推測で復元しない。共有環境で他者の更新があれば上書きせず報告する。

### 5. 結果を書く

`assets/<タスク名>/<実行日>/result.md` を作る。同じ日に2回目を回す場合は
`<実行日>-2/` のように連番を足す (上書きしない)。

```sh
J="job/<案件名>"
mkdir -p "$J/assets/<タスク名>/$(date +%F)"
```

書式は「[出力フォーマット](#出力フォーマット)」を参照。あわせてタスク md を直す。

| 選択 | 完了条件 | result.md |
| --- | --- | --- |
| 期待どおり | `[x]` | OK |
| 違った | `[ ]` のまま | **NG** + 何が起きたか |
| 確認できない | `[-]` | 確認不能 + 理由 |

* `## 完了条件` のチェックを書き換える
* `## ログ` の `#### 実施内容` に「ID × 結果」の表を追記する。
  **フェーズを足す形にして、前回の結果は消さない**
* frontmatter の `updatedAt` を当日にする
* 結果ファイルへのリンクをタスク md に置く (`../assets/<タスク名>/<実行日>/result.md`)

最後に 1:1 対応を検証する。

```sh
./.claude/skills/verify-task/check_scenario_ids.sh job/<案件名>/list/<タスク名>.md
```

### 6. 次の一手を出す

* **NG があれば実装タスクへの差し戻しを提案する。** リンクの `mv` と
  `status` の書き換えは task-transition スキルの手順で行う (このスキルではやらない)
* 「確認できない」が出たら、**理由を手順書側に書き戻すかを聞く。**
  同じことを次回また試すのは無駄なので、`#` コメントで残す価値がある
  (書き戻し自体は人の判断を待つ)
* 作業の経緯や気づきは `logs/<year>/<month>/<day>/<agent_name>/<session_id>/` に残す
  (`_.md` を複製する。結果そのものは `assets/` にあるので、ここには**判断**を書く)

## 中断する条件

以下に当たったら、その場で止めて状況を報告する。

* 前提 (ブランチ・コンテナ・ログイン・対象データ) が揃っていない
* `test:` の指すパスが存在しない、または feature が 1 つも無い
* 手順書の記述と画面が食い違っていて、どちらが正しいか判断できない
  (**手順書が古い可能性があるので、勝手に読み替えない**)
* 後片付けで元に戻せないものが出た

## 出力フォーマット

`result.md`。

```markdown
# 実行結果 2026-01-15

対象: `docs/feature/admin/item-edit/`
実行: /verify-task (対話)
環境: api `feat/PROJ-123` (abcdef0) / frontend `feat/PROJ-123` (1234567)
範囲: ADM-1-1 〜 ADM-1-4 (章 1)

| ID | 結果 | 備考 |
| --- | --- | --- |
| ADM-1-1 | OK | |
| ADM-1-2 | OK | |
| ADM-1-3 | **NG** | (4) 押下できない。非活性のまま |
| ADM-1-4 | 確認不能 | 画面幅が足りず対象が見えない |

## 環境の復元

| 対象 | 変更内容 | 復元 |
| --- | --- | --- |
| `items` id=100 | `status` draft → active | **初期値に復元** |
```

会話への報告。

```
job/PROJ-123/list/item-edit-manual-test.md
  完了条件: [x] 2 / [ ] 1 / [-] 1 を更新
  実施内容: フェーズ 4 として結果表を追記

job/PROJ-123/assets/item-edit-manual-test/2026-01-15/result.md

check_scenario_ids.sh: 1:1 で対応している
環境の復元: 1 件すべて復元済み

NG 1 件 (ADM-1-3)。frontend の実装タスクへ差し戻しますか
```
